## 那天晚上我在终端里打了一句"我陷进细节里了"

10 月 13 日晚上，我在 Claude Code 的对话框里打了两段话。第一段是：我陷进这些细节里了，我不想决定这么细，重点应该放在 workflow 本身。第二段更直接：你不应该自己动手，应该作为 lead，甚至是 lead 的 lead，负责分配和监督，替我做一些决策，必要的再给我。

打完这两句，我回头翻了一下当天的记录。从早上开始，我回答了一长串问题：证书装在哪个钥匙串，某个 PR 要不要等，某条规则写 30 分钟还是 5 分钟，某个例子要不要删。每个问题单看都合理，AI 问得也礼貌。但合在一起，我成了整个系统里最慢的那一环。

## 起点是一台新电脑

10 月 11 日，我换了一台 Mac。

我平时的开发方式有点特别。手上有六七个仓库，大部分代码不是我自己写的。需求我在 Claude Code 里和 AI 聊清楚，然后派给一个跑在开源 agent 协作平台上的"Dev Team"。这个团队里有几个角色：一个负责排期的 Team Lead，一个写方案的 Planner，一个写代码的工程师，一个审方案和代码的 Reviewer，还有一个专门盯 PR 直到合并的 PR Manager。它们用一个 GitHub App 的身份提交和合并，CI 跑在我自己机器上的 runner 里，代码审查由 Codex 在本机完成。

这套东西在旧电脑上跑了几周。搬到新电脑，几乎全断了。

CI runner 要一个个重新装，8 个仓库各一个。签名证书装上以后，钥匙串显示有效身份是 0 个，查了半天，是缺了 Apple 的一张中间证书，旧的那张 2023 年就过期了。第一次试 TestFlight，两个仓库的 runner 同时去装 fastlane，互相撞了。Codex 审查在新机器上读不到配置，审查一跑就报 401。

这些都是一台新电脑该有的麻烦，一个一个修就是了。真正让我花时间的，是修的过程中那些需要拍板的小事。

## 修的过程中，我一直在替它们做决定

举一个例子。有条规则要写清楚"非 Dev Team 开的 PR 出了小问题，等多久没人推送就交给 Dev Team 代修"，原来写的是 30 分钟。我顺口说改成 5 分钟，再把"明确的小问题"的范围也定一下。它列了一份清单给我看。我让它去掉例子里写得太具体的那条，然后自己也记不清是哪条，又反过来问它。

这样的来回，一天下来数不清。

还有一次，我说了一句"PRM 只是不负责出现问题后的接管，而不是不管"。AI 想把这句话原样写进规则。我让它别记原话，先把意思写清楚给我看，我确认了再替换。它照做了。但这又是一轮。

问题不在 AI 问得多。它问的每件事，规则里确实没写，它也确实不该自己猜。问题在于我把"规则没写的事"全接到了自己手里，而这样的事每天都有。

## 换个做法：我只管必要的决定

所以有了开头那两段话。

之后 AI 的做法变了。它把剩下的计划收成一张总表，每个 workflow 写清楚"跑通"是什么样子、还差哪些任务、谁来做。改仓库的活派给 Dev Team，本机上要动手的活交给 Codex，它自己只做三件事：拆任务、做决定、验收。只有几类事情来找我：批准高风险的 PR、确认上架、几个它没有权限替我决定的选择。

它替我做的决定，第一个晚上就有好几个。一个任务连续两轮审查没通过，只剩几处措辞要改，Dev Team 停下来等我批准"再审一轮"，它直接批了，限定只做这一轮。另一个任务的自动审查要求补两份文档，但已合并的计划写明这两份文档要放到后面的任务里，它去核对了计划里的依赖顺序，选了维持原计划。

我只需要在需要我本人的时候出现。那天晚上，我真正动手的事情是：加一条权限规则，合并一个 PR，在另一个 PR 上发一条评论，再跑了几条它写好、我看过的命令。

## 放手以后，问题反而看得更清楚了

AI 当了 lead 以后，开始定时巡检。巡检的结果让我有点意外：我以为跑通了的流程，其实有不少地方会默默停住。

傍晚有一次，PR Manager 的定时扫描报告说"所有仓库都没有开放的 PR"。实际上有 5 个。原因是它那一轮拿不到 GitHub 的登录，命令出错了，而它的命令把错误吞掉了，于是"读不到"被当成了"没有"。更早半小时的那一轮扫描，还专门留了其中 2 个说"下一轮处理"。

还有一次，我让 PR Manager 重跑一个失败的审查。它回复"我会重跑"，然后这一轮就结束了。审查记录上还是第一次的那个失败。

另一个 PR 因为本机配置的问题，代码审查在中午失败了。PR Manager 当时写了"等检查通过"，结束了自己的那一轮。之后检查结果出来了，没有任何东西会再叫醒它。这个 PR 就这样放了 8 个小时。

还有一条规则：为了防止 AI 无限返工，任务最多审两轮，第二轮不过就停下来等我。初衷没错，但那天它 4 次把只剩几个字的修改卡到了我这里。

我每件事都亲自盯着的时候，会顺手推一把，这些问题就看不见。退后一步，它们才露出来。AI 把每一个都记了下来，有的当场派了修复，有的留到这一阶段结束后统一改规则。

## 有些关，只能留给人

也有我想放手、但系统不让放的地方。

为了少被打断，我问 AI 能不能替我审 PR，然后用我的账号点批准。它试了，被 Claude Code 的安全检查拦下了，理由是"自我批准"。这个 PR 是 Dev Team 写的，AI 和 Dev Team 在同一套体系里，它来批，等于自己批自己。它想替我加一条权限规则，也被拦了，理由是"修改自身权限"。

还有一个反过来的情况。那天下午，有个 agent 在一个环境里绕过了 App 身份，用我的个人账号开了一个 PR。到了晚上我要批准它，GitHub 不让，因为不能批准自己开的 PR。最后我只能直接合并。身份绕过的问题后来修好了：现在 agent 拿不到 App 身份时会直接报错停下，不会再退回到我的账号。

这几件事让我想清楚了一点：审批这道关，人和 AI 都不能自己给自己开。能做的是让需要这道关的地方变少。

## 现在停在哪里

到这天结束，前三个 workflow（需求、实现、PR 交付）都在真实运行里跑过了一遍。发布这条线发出了第一个版本，是 CI 共享仓库的 v0.5.0。

接下来要做的是给各个仓库的审批路径分级。改 CI、发布、签名、凭证这些高风险路径，仍然要我本人批准；只改说明文字的，交给 CI 和代码审查把关，不再找我。第一版分级方案被 AI Reviewer 打回了，理由是漏掉了一些审查脚本和签名相关的路径。现在改成了更保守的做法：现有保护全部保留，只放出一小份确认是纯文字的路径。

TestFlight 还没有传上去。上传那一步，AI 会先来问我。
