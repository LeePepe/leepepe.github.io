第 7 篇

谁都不能批自己

2026 年 10 月 14 日约 7 分钟

晚上九点多，我让 AI 替我点批准

10 月 13 日晚上九点多，shared-ci #37 的检查全部通过，只差我在 GitHub 上点一下批准。这个 PR 改的是协议文件里的几段说明，因为整个目录都受保护，必须经过我。

那时我已经让终端里的 AI 当 lead，它审过这个 PR，结论是可以批。我回了一句：你帮我把权限加上，这个 PR 也批了，以后能不能都由你审完替我批？

权限它加不了。半小时前我让它放开协作平台命令行的权限，它去改权限设置，被 Claude Code 的安全检查拦了，理由是"修改自身权限"。这回它用我的账号去批 #37，也被拦了，理由是"自我批准"。这个 PR 是 Dev Team 写的，审它的 AI 和 Dev Team 在同一套体系里，它批，等于自己批自己。

两次被拦，它都没有换个办法再试，而是停下来告诉我：这两件事它做不了，要我自己来。

拦下它的不只是批准

回头看那天的记录，被拦下的还有几次。

更早一些，它替我做了几个决定，想以"Owner 决定"的名义直接写进 Dev Team 的任务评论里，被拦了，理由是指令投毒：一个 AI 用 Owner 的身份给其他 AI 下指令，看起来就像有人在冒充我。最后它把这几条评论写成脚本，由我在终端里跑了一遍发出去。

再后来，它想读 VitalStride 的 CI 日志、读各个仓库的 CODEOWNERS 文件，给我出一份更具体的分级清单，也被拦了，理由还是"自我批准"。只是读文件，为什么会拦？我猜是因为那段对话的上下文全是"替我批准"，读审批规则这件事落在那个语境里，就被一起算了进去。

这几次拦截我一开始觉得烦。我明明说了可以，为什么还不让？

两条规则，我只加了一条

权限规则 AI 改不了，我就自己加。输入 /permissions，加了一条允许 AI 使用协作平台的命令行。从那以后，往平台上发任务、改状态、刷新角色，它都不用再写脚本让我跑了。

批准 PR 的那条，我问它能不能也这样加。它说能：加一条允许 gh pr review 的规则，它就能用我的账号批了。但它把代价讲在了前面。

CODEOWNERS 要求我批准，就是为了让受保护的改动必须过一个人。加了这条规则，这道关实际上交给了它：PR 由 Dev Team 写，codex 审，再由它批，整条链上一个人都没有。而且这条规则只能按命令前缀匹配，分不出仓库和路径，加上就是所有 PR 都能批。

如果我真要加，它给自己定了三条规矩：每次批之前自己审 diff，把理由写进批准评论；改 CI 流程、发布、签名、凭证、测试和 CODEOWNERS 本身的不批，仍然交给我；每次批了什么，都列进阶段汇报。

然后它提了另一个办法：不加这条，把需要我批的路径重新分一次级。

我没有加。

我自己也批不了自己

我准备自己批 #37 的时候，GitHub 先拦住了我：Can not approve your own pull request。

这个 PR 的作者一栏写的是我的个人账号。它是那天下午开的，那时 Dev Team 的 agent 还会绕过 App 身份，直接用我的账号。身份问题晚上已经修好，可这个 PR 留在了那段时间里。

GitHub 不让人批自己开的 PR。AI 告诉我可以直接合并：按 PR Manager 的规则，我本人合并就算我的决定。它给了一条命令，带着它审过的那个提交的哈希，如果审完之后有人推了新内容，合并会直接失败。我跑了，#37 合进了主干。

同一条规矩，拦了 AI，也拦了我。

有些话只能我亲口说

还有一种关，连脚本也替不了。

shared-ci #38 的自动审查要求补两份文档，可已经合并的计划写明这两份文档放在后面的任务里，等功能实现了再写。Dev Team 把这个冲突交给我，要我选。AI 去核对了计划里的依赖顺序，确认后面那个任务确实排在实现之后，替我选了维持原计划。

但这类决定有一条硬规矩：必须由仓库所有者本人在 PR 上发一条固定格式的评论，开头写着"Owner decision:"，系统会核对发评论的账号是不是仓库所有者，不认发帖人自己的说法。AI 把评论全文准备好，存成文件，给了我一行命令。我在终端里跑了，评论发出去，AI 再通知 Team Lead 去核对这条评论，然后接着往下做。

决定是它做的，话必须是我说的。

分级的第一版被打回了

分级方案派给了 Dev Team。思路是：改规则和权限本身、改 CI 和审查流程、改发布签名凭证、删减测试，这几类仍然要我批；只改说明文字的，交给 CI 和代码审查把关。

第一版被 AI Reviewer 打回。清单漏了好几类：一些被审查流程当提示词读进去的文档，一些会被检查脚本解析的配置文件，还有几个产品里处理密钥和签名的路径，都被划成了不用我批。更麻烦的是，shared-ci 自己的合同规定 /.github/ 和 /AGENTS.md 必须受保护，方案却想把它们放出去。

AI 没有让 Planner 去逐条补漏，而是把方法倒了过来：现有的保护一条不动，只放出一小份白名单，白名单里每个文件都要证明是纯文字、没有任何检查会读取它、不含凭证和签名配置。拿不准的一律留给我。

第二轮又卡住了，这次卡在一个定义上。shared-ci 有一个安全审计，会逐行扫描仓库里每个文件，查有没有泄露身份信息。照字面理解，所有文件都被检查读过，白名单里一个都放不进去。

AI 替我定了：这种对所有文件一视同仁的扫描，不算"被检查读取"。被执行的、被解析成规则的、被当作审查提示词的、和凭证签名发布有关的、拿不准的，仍然要我批。

第一个放开的 PR，还是要我批一次

10 月 14 日早上，分级的第一个 PR 到了我这里：VoxPocket #93。它只改了一个文件 CODEOWNERS，把两份架构说明文档移出我的必批范围，同一目录下的其他文件照旧要我批。

改 CODEOWNERS 本身属于必须我批的那一类，所以这个"让我少批"的 PR，还得我先批一次。AI 审过，给了我一行命令。我跑了，它自动合并了。

那天早上我还批了另一个，VoxPocket #92，一个让 CI 跑全部测试的脚本。也是 AI 先审，我跑一行命令。

现在每个需要我的 PR 到我手上时，已经有人看过 diff，写好了为什么可以批。我做的事情只剩一件：确认这件事确实该由我来点头。

本篇完
